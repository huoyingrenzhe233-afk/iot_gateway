# 网关主程序代码审查报告 — 稳定性与 Web/Qt 双端专项

> 审查范围:iot_gateway 全部 C++ 源码(12 模块 + main.cpp)、web/index.html、qt/(空壳)、配置文件、构建脚本
> 审查重点:① 崩溃 ② 卡顿 ③ 线程安全 ④ Web/Qt 双端并存时的数据不同步与指令冲突
> 方法:逐文件通读 + 对照 vendored mongoose 7.20 源码逐条核实 API 行为(非推测)
> 说明:按用户要求,恶意利用类安全问题(注入/无鉴权/DoS)不在本次范围,仅顺带备注

---

## 一、总体结论

架构方向正确:mongoose 单线程事件循环 + SQLite 队列写线程是当前代码规模下最不容易出错的组合;MQTT 断线重连/心跳、WS 广播清理、子进程僵尸收割、JSON 转义等关键路径都做得扎实,历史审查也修掉了一批真 bug。

**但存在 3 个「一次点击就能冻结/杀死整个网关」的高优先级问题,全部集中在摄像头进程管理和 ZigBee 串口发送这两个「事件循环里的阻塞等待」上**,以及 1 个双端状态被错误更新导致的「假同步」问题。此外,双端并存时 /api/control 全量覆盖的指令冲突、通道切换状态不广播、摄像头接口命名与老师文档不一致,是联调时最可能踩的坑。

## 二、🔴 高优先级(建议本周内修)

### H1. 抓拍接口可冻结网关最长 15 分钟(卡顿→服务完全停摆)

**位置**: src/core/camera/camera_manager.cpp:268 snapshot()

snapshot 在 HTTP 回调里用阻塞 waitpid(pid, &st, 0) 等 wget 退出。wget 命令只带了 -q,**默认读超时是 900 秒**。正常路径(流在跑)约 0.2s 返回;但若 mjpg_streamer 进程活着却卡住(摄像头异常/挂起),TCP 连接已建立、无数据返回,连接拒绝不会发生,wget 会挂到超时为止。

后果:Web 或 Qt 上点一次「抓拍」,整个事件循环(HTTP + MQTT + WS + 定时器)全部冻住最多 15 分钟——健康检查无响应、上报中断、控制命令下发失败,与「网关死机」无异。

**修复建议(任选其一)**:
1. 最简单:wget 加 -T 5(总超时 5 秒),一行改动;
2. 更彻底:spawn 后仿照 stop_child 用 WNOHANG 轮询 + 超时 SIGKILL,把等待上限压到 3~5s;
3. 最彻底:抓拍也异步化(mg_timer 回调里探测 wget 退出后再回填文件名),但需要给 HTTP 响应挂起机制,课程项目用方案 1 即可。

### H2. 停流/停录像在事件循环里同步等最多 3 秒(卡顿)

**位置**: src/core/camera/camera_manager.cpp:144-169 stop_child(),被 stop_stream()/stop_record() 以 3000ms 超时调用

M1 修复把「阻塞 waitpid」改成了「50ms 轮询 + 3s 超时 + SIGKILL 兜底」,方向对,但**等待过程本身仍发生在 HTTP 回调里**。每次点「停止推流/停止录像」,HTTP、MQTT、轮询、WS 全部冻结最多 3 秒;若期间恰好还有前端 1s 轮询,表现为整页卡顿、日志「掉线」假象。

另外第 166 行 waitpid(pid, NULL, 0) 仍是无超时阻塞:SIGKILL 后若子进程处于 D 状态(不可中断 IO,如 eMMC 写卡死),这个 waitpid 永远不会返回 → 网关永久冻结。

**修复建议**:把停止流程改成真正的异步:发出 SIGTERM → 立即返回 200 → 用 mg_timer(每 100~500ms)探测退出并在超时后 SIGKILL,状态字段在事件循环线程更新,天然线程安全。至少把 166 行的阻塞 waitpid 换成 WNOHANG 轮询(超时后放弃,交给 reap_children 兜底)。

### H3. ZigBee 通道下,一次发送最多阻塞事件循环 5 秒(卡顿)

**位置**: src/core/channel/zigbee_adapter.cpp:111-133 send()

EAGAIN 重试上限 100 次 × poll 50ms = **最多 5 秒**阻塞在事件循环里。切到 zigbee 通道后,每一次 /api/control、/api/actuators/:id/set、规则动作都会走这里。DL-30 拔掉/对端不读导致写缓冲满时,一次用户操作就能把网关冻 5 秒(而且最后返回 false,命令其实没发出)。

**修复建议**:
1. 短平快:单次 send 的阻塞预算压到 ≤100ms(2 次 poll),失败立刻返回 false;
2. 正解:待发消息进 std::deque<std::string> 队列,在已有的 50ms poll 定时器里续写未发完的数据(串口写本身就是可重入的分片操作,天然适合)。这样事件循环永不阻塞,还能顺便获得「通道未就绪时缓存最近 N 条命令」的能力。

### H4. 规则动作不检查下发结果 → 命令没发出却把缓存改了(双端「假同步」)

**位置**: src/gateway/main.cpp:838-843(g_rules.on_action)对比 main.cpp:458-484(/api/control)、main.cpp:344-369(/api/actuators/:id/set)

/api/control 和单执行器接口都先检查 send_to_mcu 返回值,失败回 503 且**不改缓存**;但规则动作回调直接:

    g_channel.send_to_mcu(envelope);          // 返回值被丢弃
    g_device.update_from_control(envelope);   // 无条件更新缓存

MQTT 掉线(或 zigbee 未插)期间,规则照常触发 → 命令根本没到单片机,但 /api/status 已经显示 buzzer=1 / led=1。Web 和 Qt 两个客户端都会看到「蜂鸣器响了」,实际硬件纹丝不动,而且没有任何日志能区分这是「已下发」还是「仅缓存」。这是目前**双端数据不同步的唯一确定性问题**。

**修复建议**:与另外两条路径对齐——检查返回值,失败 LOG_WARN 且不调用 update_from_control。

## 三、🟡 中优先级(线程安全 / 健壮性)

### M1. 多线程进程里 fork,子进程在 exec 前调用 malloc(潜在死锁/僵尸)

**位置**: src/core/camera/camera_manager.cpp:51-91 spawn()

进程里常驻 SQLite 写线程。fork 后子进程只继承调用线程;若 fork 瞬间写线程恰好持有 glibc malloc arena 锁,子进程里任何 malloc 都会永久死锁。而子进程 exec 前恰恰做了:

    std::vector<char *> cargv;
    cargv.reserve(argv.size() + 1);   // ← malloc
    cargv.push_back(...);             // ← malloc
    execvp(...);                      // glibc 实现内部也可能 malloc

后果:概率低,但一旦命中,子进程永远卡在 fork/exec 之间,成为「永不退出」的僵尸;父进程拿到的 pid 永远探测为「还在运行」,start_stream/stop_stream 全部进入 3s 等待路径,录像文件永远写不完。

**修复建议**:改用 posix_spawn()(专为此场景设计);或者退一步,fork **之前**在父进程里把 char* argv 数组构造好(此时 malloc 安全),fork 后子进程只做 close/open/dup2/execv 这些 async-signal-safe 调用。

### M2. SqliteStore::enqueue_telemetry 无锁读 db_(唯一一处锁外共享访问)

**位置**: src/core/storage/sqlite_store.cpp:142

其它路径读/写 db_ 都在 db_mutex_ 内(shutdown 还会把它置 nullptr),唯独 enqueue 裸读。当前 main 永不退出、shutdown 从未被调用,实际不存在并发窗口;**但这是全项目唯一一处跨线程共享数据的锁外访问**,将来若接入信号处理(SIGTERM → shutdown)就会变成真实数据竞争。

**修复建议**:db_ 改成 std::atomic<sqlite3 *>(或 enqueue 内先加 db_mutex_ 判空——注意锁顺序,enqueue 只持有 queue_mutex_,不会死锁)。同时建议给 pending_ 队列加上限(如 10000 条,超限丢最旧):磁盘卡死导致写线程停摆时,队列无限增长会撑爆内存。

### M3. 子进程 PID 复用导致的误杀(低概率,理论真实)

**位置**: src/core/camera/camera_manager.cpp:150,165 与 src/gateway/main.cpp:132 的交互

reap_children 每 5s 用 waitpid(-1, WNOHANG) 收割所有子进程;stop_child 手里拿的 stream_pid_ 若在收割后、kill 前被内核复用给新进程(比如刚 fork 的 wget),SIGTERM/SIGKILL 会打到无辜进程。单线程 + 嵌入式低进程量下概率极低,但这是「用 pid 管理子进程」的固有缺陷。

**修复建议**:kill 之前先 waitpid(pid, WNOHANG) 探测一次(已退出就按 ECHILD 处理);更稳的做法是记录 fork() 时子的启动时间(/proc/<pid>/stat 的 starttime)或子进程持有一个继承的私有管道,通过管道 EOF 判断「是不是我那个子进程」。

### M4. MqttClient 不区分连接代次(潜在,当前不可达)

**位置**: src/core/common/mqtt/mqtt_client.cpp:150-157

任何 MG_EV_CLOSE 都会无条件 conn = nullptr; subscribed_ = false。若「旧连接的 CLOSE 事件」晚于「新连接的 OPEN 事件」到达(快速重连场景),会把正在工作的新连接状态误清掉,导致 5 秒内命令全被 503、且再拉起一条多余连接。当前代码路径(connect 只被 main 调一次;重连仅在 conn==nullptr 时发生)下**不可达**,属加固项。

**修复建议**:给每次 connect 分配自增代次号 uint64_t gen_,回调里核对连接指针或代次,不匹配的 CLOSE 直接忽略。

### M5. 启动时监听失败静默(端口被占 = 网关「活着但死了」)

**位置**: src/gateway/main.cpp:855

mg_http_listen(...) 的返回值被丢弃。8080 被 mjpg_streamer 占用这个坑在 HANDOFF 里出现过一次,如果哪天板上有人忘记传 8081 参数,或端口被残留进程占住,网关会**正常进入事件循环但没有任何 HTTP 服务**——MQTT 还在跑、日志还在刷,只有健康检查打不通,排障极其迷惑。

**修复建议**:两行——检查返回值,为 null 时 LOG_ERROR 并 exit(1)。(g_registry.load / g_rules.load 失败已记日志但继续跑,可接受;监听失败不可接受。)

### M6. zigbee 拔线后日志刷屏(20 条/秒)

**位置**: src/core/channel/zigbee_adapter.cpp:150-182 poll_serial()

模块被拔/串口出错后,read 持续失败,**每 50ms 打一条 LOG_WARN**,一天能刷 170 万行,叠加 logger 每行 flush,会把 gateway.log 和 flash 迅速写满,间接拉慢整个系统。

**修复建议**:连续失败计数,失败 N 次(如 20 次)后暂停轮询并降频重试(如 1s 一次探测),恢复后归零。

### M7. 进程收到 SIGTERM 无任何收尾(部署脚本就是这么杀的)

**位置**: src/gateway/main.cpp(无 signal handler);build-arm.sh:32 pkill -x gateway

pkill 默认发 SIGTERM → 进程立即死亡。WAL 模式保证库不损坏,但 pending_ 队列里最后 ≤1s 的遥测数据丢失、未 checkpoint 的 WAL 留在盘上。课程演示无碍,但 shutdown() 已经写好了,只差一个 signal handler 调用它(注意:signal handler 里只置标志,真正 shutdown 在事件循环里做,避免在信号上下文里 join 线程)。

## 四、🔵 Web/Qt 双端专项:数据不同步 & 指令冲突

### 4.1 指令冲突矩阵

| # | 冲突场景 | 现状 | 后果 | 建议 |
|---|---|---|---|---|
| D1 | **双端全量控制互相覆盖** | Web 面板每次改动都发全量 6 字段 /api/control(index.html:553-583);若 Qt 照抄 API 文档 §13 的「完整设置面板用 /api/control」,两个客户端的「全量快照」互为最后写入者 | A 端把亮度调到 30,1 秒后 B 端为开蜂鸣器用自己 1 秒前的旧快照(亮度 50)覆盖回 50 → A 端屏幕上的亮度自己跳回去 | 网关无 per-client 状态,无法仲裁。**最低成本方案:双端约定只发变更字段(partial)**,或全部走 /api/actuators/:id/set;网关侧可选加「每字段 seq/updated_at」,客户端只应用更新的值。API 文档 §13 建议 Qt 用单执行器接口,方向已对,联调前把它变成硬性约定并写进调试手册 |
| D2 | **规则引擎 vs 手动控制** | 边沿触发(rule_engine.cpp:296-304)已缓解持续打架,但每次条件跨越阈值都会 fire 一次,覆盖用户的手动设置 | 用户手动关灯后,光照下一次穿越阈值,灯又被规则打开;Web/Qt 界面滑杆「自己动」,用户会以为网关坏了 | 现状可接受,但要:① 在 WS 广播规则触发事件(如 {"type":"rule","rule_id":...}),让 UI 显示「此状态由联动产生」;② 可选给规则加冷却时间/手动挂起(已有 /api/rules/:id/enable 可临时禁用)。至少把该行为写进联调说明,别让 Qt 同事当 bug 报 |
| D3 | **双端并发切通道** | /api/channel/switch 后写者胜;另一端的按钮只在页面加载时查一次 /api/channel(index.html:712),之后**永不刷新** | 一端切了 zigbee,另一端按钮还显示 MQTT,再点一下又切回去,来回拉扯 | 见 4.2-③:通道变化通过 WS 广播 + /api/status 附带 transport 字段,两端都能秒级收敛 |
| D4 | **同 1 秒并发抓拍** | 文件名 snapshot_<秒级时间戳>.jpg(camera_manager.cpp:251) | 两个客户端同一秒抓拍,后写覆盖先写,先拍的「成功」照片没了 | 时间戳加毫秒或 pid 后缀,一行改动 |

### 4.2 数据不同步风险点

① **乐观缓存 vs 回执校准(设计已知,建议显式化)**:update_from_control 让 /api/status 秒级反映「命令意图」,单片机 status 回执约 2s 后覆盖校准;命令实际失败时,双端会看到「状态先变、又回退」。HANDOFF #25 记录过「回执覆盖下发值」。**建议**:API 文档 §4.4 明确写「轮询值 = 网关缓存(乐观值),以回执为准,可能出现短暂回退」;有精力的话给 /api/status 加 pending/seq 标记区分「已确认/待确认」。

② **start_record 不校验推流状态(双端短暂失步)**:camera_manager.cpp:192-196 只查 record_running(),流没启动也 fork ffmpeg 并返回 {"ok":true};ffmpeg 连接失败立刻退出,前端 recordStarted=true 要等 5s 后下一次 /api/camera/status 轮询才被纠正。**建议**:start_record 前先 stream_running(),未推流返回 500/409 + message。

③ **通道切换不广播(双端长期失步)**:网关已有 ws_broadcast 基础设施,切换成功时广播 {"type":"channel","transport":"..."} 是几行改动;同时让 /api/status 多带一个 transport 字段,让只轮询的 Qt 也能收敛。收益:双端按钮永远一致。

④ **抓拍文件拿不到(文档与实现不一致)**:main.cpp:662 注释和 API 文档 §7 都写「前端可拼 http://<host>:8081/snapshots/<文件名> 展示」,但网关**没有任何 /snapshots 静态路由**,拼出来就是 404。要么加静态目录伺服,要么删掉文档承诺。Qt 同事按文档做预览会踩空。

⑤ **摄像头接口命名与老师 project-plan.md 不一致(联调地雷)**:老师 plan.md(第 788-793、892-897 行)写的是 POST /api/camera/start|stop、/api/camera/record/start|stop;项目实现和 web 前端用的是 start_stream|stop_stream|start_record|stop_record(以 standard/index.html 为准,HANDOFF 有记录)。**若 Qt 同事按老师文档写客户端,四个接口全是 404**。同理老师验收示例用的设备 id 是 temp/led(plan.md:447-450),项目登记表是 temp_1/led_1。**建议**:网关加别名路由兼容两套命名(或至少开会通知 Qt 同事 + 在 API 文档 §7 顶部红字标注差异),低成本消除验收风险。

⑥ **轮询覆盖本地操作(前端已有雏形,Qt 必踩)**:index.html:627-658 每 1s 轮询并把 data.led_br ?? 50 等值写回控件——用户正拖动滑杆时,一次带旧值的轮询返回会把滑杆拽回去。Qt 实现时建议:控件获得焦点/正在拖动时跳过状态回写,或比较状态时间戳。这是双端各自要防的 UI 竞态,写进对接文档。

⑦ **WS 只推「收到上报」**:命令下发、规则动作、通道变化都不进 WS。Qt 若想实时看到「另一个客户端的操作」,只能靠 1s 轮询,存在 1s 盲区 + 与本地操作竞态。可选增强:统一事件流(上行 report + 下行 cmd + rule + channel),一劳永逸解决双端同步,工作量中等,建议列为下一轮迭代。

### 4.3 接口健壮性(双端联调常见翻车点)

- POST /api/actuators/:id/set 的 {"value":"1"}(字符串):mg_json_get_tok 判存在通过,但 mg_json_get_long 对字符串 token 返回默认值 0 → **下发「关」**。已核实 mongoose 实现(mongoose.c:2929-2937 要求 token 首字符为数字或 '-')。Qt 同事用 QJsonValue::toString 误转很常见。**建议**:服务端校验 value 必须是数字类型,否则 400(而非静默发 0)。
- /api/control 的 payload 数值类型同理(字符串值会以 0 进入缓存)。
- /api/rules/reload 后 last_satisfied 全部归零(rule_engine.cpp:243):当前仍满足条件的规则会在 reload 后第一次上报时**重新 fire 一次**,表现为蜂鸣器/灯闪一下。幂等命令无实际危害,联调时别误判成 bug,备注即可。

## 六、已验证安全(核对结论,不必改)

- **单线程事件循环模型**:HTTP/MQTT/WS/定时器回调同一线程,设备缓存、规则、通道、摄像头 pid、g_ws_clients 均无跨线程访问 → 无数据竞争。唯一跨线程共享是 SQLite 队列(锁 + 条件变量)与 stop_(atomic),实现正确。
- **SQLite**:WAL 模式;单连接 + db_mutex_ 串行化(无 sqlite 回调重入,不会死锁);写线程批量事务、优雅 flush 逻辑正确。
- **MQTT**:5s 断线重连 + 30s PINGREQ 兑现 keepalive=60(周期性断连已修);CONNACK 非 0 时 mongoose 自断 + 重连循环;发布前 is_connected() 防御,掉线窗口命令被 503 拒绝而非假成功。
- **WS**:EV_CLOSE 清理列表、发送缓冲超 3MB 时 mongoose 自动关连接(mongoose.c:9729)→ 死客户端自愈;广播消息过 json_escape;mg_json_get_str 的 malloc 内存所有调用点均 free(逐点核对,无泄漏/双重释放)。
- **路由**:reload 排在 :id 路由前、精确匹配优先,无路由遮蔽;id 提取器均有边界检查。
- **摄像头进程管理**:fork+execvp(无 shell 注入)、子进程关 fd、僵尸收割、stale pid 探测清理——结构正确,问题只在「等待方式」(H1/H2)。
