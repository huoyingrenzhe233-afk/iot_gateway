## 1. 一句话总览

**这是一个"翻译官"程序**:一边对 Web/Qt 说 HTTP,一边对单片机说 MQTT,中间靠内存缓存传递信息。

```
Web/Qt ──HTTP──→ 网关 ──MQTT──→ 单片机
                 (你写的)
Web/Qt ←──HTTP── 网关 ←──MQTT── 单片机
```

## 3. 程序启动流程(从开机到跑起来)

main.cpp 第 148-208 行,一步步:

```
main() 开始
  │
  ├─ ① load_config()         读 config/gateway.yaml → Config 结构体
  ├─ ② Logger::init()        开日志文件 gateway.log
  ├─ ③ 解析端口              命令行参数优先(板上 8081),否则用配置(8080)
  ├─ ④ mg_mgr_init()         创建 mongoose 事件管理器(总控台)
  ├─ ⑤ g_mqtt.connect()      MQTT 客户端连 mosquitto(127.0.0.1:1883)
  ├─ ⑥ g_device              创建设备状态缓存(static,常驻)
  ├─ ⑥.5 g_registry.load()   读 sensors/actuators.yaml → 设备清单
  ├─ ⑦ g_mqtt.on_message = 设置回调:收到 MQTT 消息 → 更新设备缓存
  ├─ ⑧ mg_http_listen()      启动 HTTP 服务器(端口 8080/8081)
  └─ ⑨ for(;;) mg_mgr_poll() ★ 死循环:驱动一切(永不退出)
```

**关键理解**:第 9 步的死循环是**整个程序的引擎**——HTTP 请求、MQTT 消息、定时器,全部在这个循环里被分发到各自的回调。**程序没有"多线程",所有事情都在这个循环里顺序发生**。

## 4. 数据流:两个方向,两条链路

### 4.1 下行:Web 控制 → 单片机(控制链)

```
① Web/Qt 发:POST /api/control {"type":"control","body":{"led_on":1}}
      ↓
② main.cpp request_handler() 匹配到 /api/control 路由(101 行)
      ↓
③ control.build_control_envelope() 组 MQTT 信封(control.cpp)
   {"type":"cmd","dev":"mcu01","ts":"...","body":{"led_on":1}}
      ↓
④ g_mqtt.publish() 发布到 topic dev/mcu01/cmd(mqtt_client.cpp 64 行)
      ↓
⑤ 单片机收到,执行(灯亮)
      ↓
⑥ (同时)device.update_from_control() 更新缓存 —— /api/status 立即反映(不等回执)
```

### 4.2 上行:单片机上报 → 网关缓存(上报链)

```
① 单片机发:dev/mcu01/report {"type":"sensor","body":{"data":{"temp":25.6,...}}}
      ↓
② mongoose 触发 MqttClient::event_handler()(mqtt_client.cpp 85 行)
      ↓
③ handler_event() 收到 MG_EV_MQTT_MSG → 取出 topic/payload
      ↓
④ on_message 回调被调用(main.cpp 187 行设的 lambda)
      ↓
⑤ device.update_from_report() 解析信封 → 更新内存缓存(device.cpp 17 行)
      ↓
⑥ Web/Qt 轮询 GET /api/status → get_status_json() 返回缓存(main.cpp 84 行)
```

### 4.3 状态校准链(回执)

```
Web 发命令 → 单片机执行 → 单片机回执 status(items)→ 网关 update_from_report
→ 覆盖缓存(以实际执行为准,而不是网关猜的)
```

**为什么有回执**:命令 ≠ 结果。灯可能执行失败、可能被按钮改了、可能掉线重启——只有单片机回执是真相(详见 HANDOFF"状态同步方案")。

## 5. 核心类关系图(谁引用谁)

```
                         main.cpp(总指挥)
                              │ 持有
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                      ▼
   MqttClient            Device                DeviceRegistry
 (MQTT 通信)          (状态缓存)              (设备清单)
        │ 暴露 on_message        │ get_status_json()    │ to_json_list()
        │ 回调(由 main 赋值)      │ update_from_report() │
        ▼                        ▼                      ▼
   mongoose 事件循环 ◄──── 所有回调都在这里被驱动
   (mg_mgr_poll)
```

| 类 | 职责 | 谁用它的什么 |
|---|---|---|
| `MqttClient` | 连 broker、订阅、发布、重连 | main 调 `connect/publish`;main 设 `on_message` |
| `Device` | 存传感器/执行器状态 | `on_message` 调 `update_from_report`;/api/status 调 `get_status_json` |
| `DeviceRegistry` | 存设备清单 | /api/devices 调 `to_json_list` |
| `Config` | 存配置值 | main 启动时读,传进 HttpContext |
| `Control` | 组控制信封 | /api/control 路由调用 |
| `Logger` | 打日志 | **所有模块都调**(LOG_INFO 等宏) |

**核心关系就一句**:main.cpp 把一切粘起来——它创建对象、把回调接好、把上下文(fn_data)传进 mongoose 回调。

## 6. 两个关键机制(必懂)

### 6.1 回调机制:程序怎么"响应"事件

mongoose 是**事件驱动**的,你的代码不是主动问"有消息吗",而是**注册回调,等 mongoose 叫**:

```
你注册:mg_mqtt_connect(..., event_handler, this)
          │ 告诉 mongoose:连接的事都叫这个函数
          ▼
mongoose 循环:收到 MQTT 消息 → 调用 event_handler(c, ev, ev_data)
          │ ev 告诉发生了什么(MG_EV_MQTT_MSG = 收到消息)
          │ ev_data 是详细数据(消息内容)
          ▼
你的回调处理完,返回 → mongoose 继续循环
```

**回调的"接线"方式(fn_data)**:
```cpp
// 注册时把 this 传进去
mg_mqtt_connect(..., event_handler, this);   // this → c->fn_data
// 回调里取回来
MqttClient *self = static_cast<MqttClient *>(c->fn_data);  // 拿回 this
```
这是 C 库(C 没有对象)对接 C++ 的标准做法。

**HttpContext 也是同一个套路**:main 把 `{config, mqtt, device, registry}` 打包,通过 `mg_http_listen` 的 fn_data 传给 HTTP 回调——**所以回调里能访问到配置和设备**。

### 6.2 单线程事件循环:为什么不用加锁

```
for(;;) {
    mg_mgr_poll(&mgr, 1000);   // 所有回调在这一个线程里顺序执行
}
```
- HTTP 回调、MQTT 回调、定时器回调**都在同一线程**,任意时刻只有一个在跑
- **所以 Device 缓存被 on_message 写、被 /api/status 读,天然不会冲突,不需要锁**
- 代价:**回调里不能干耗时的事**(sleep/大计算),否则整个程序卡住

## 7. 数据从哪来:配置 + 登记表

### 7.1 config/gateway.yaml(运行时配置)

```yaml
server:
  port: 8080          # HTTP 端口(板上用 8081 避开摄像头)
mqtt:
  broker: "mqtt://127.0.0.1:1883"   # 连板上的 mosquitto
  topic_report: "dev/mcu01/report"  # 订阅:单片机上报
  topic_cmd: "dev/mcu01/cmd"        # 发布:控制命令
device:
  id: "mcu01"         # 固定设备号
log:
  level: "INFO"       # 日志级别
```

### 7.2 config/devices/*.yaml(设备清单)

```yaml
sensors:              # 4 个传感器(温湿度一体出 2 条)
  - id: temp_1        # 规则引擎引用的 id
    kind: sensor
    protocol: mqtt
    description: 温度(温湿度传感器)
  ...
actuators:            # 3 个执行器
  - id: led_1
    kind: actuator
    ...
```

**注意**:登记表 id(`temp_1`)和 MQTT 字段名(`temp`)是**两套标识**——登记表给前端/规则用,字段名给解析用。⚠️ 规则引擎的 id→字段映射还没定义(见 HANDOFF 待办)。

## 9. 今天踩的坑(必读,答辩素材)

### 9.1 连接 1 秒断一次 → 两个进程同 client_id 互踢
- 现象:MQTT 连上 1 秒就被断,无限重连
- 原因:板上残留的 `gateway_arm` 老进程和新 `gateway` 进程**用同一个 client_id**(gateway-1),MQTT 规范同 id 只允许一个连接,互相踢
- 解决:`pkill -x gateway_arm` 杀掉残留
- 教训:部署脚本清理要全;client_id 要唯一

### 9.2 mongoose API 版本坑(mg_str 是 .buf 不是 .ptr)
- 现象:编译报错 `mg_str has no member ptr`
- 原因:mongoose 7.20 的 `mg_str` 字段是 `buf`,老版本是 `ptr`
- 教训:**写代码前先查头文件,别凭记忆**

### 9.3 JSON 解析:字符串 vs 数字
- 现象:传感器值(数字)用 `mg_json_get_str` 取不到,返回 null
- 原因:那函数只处理字符串值;数字要用 `mg_json_get_num` 取 double
- 教训:先搞清楚值类型再选解析函数

### 9.4 回执遍历的 -1 陷阱
- 现象:items 里某个 value 是 -1,后续项全丢
- 原因:`mg_json_get_long(json, path, -1)` 用 -1 当"越界信号",但 -1 也可能是合法值
- 解决:改用 `mg_json_get_tok` 先判断节点是否存在
- 教训:**默认值不能和合法值冲突**(双重语义是 bug 温床)

### 9.5 防火墙/代理/SSH(环境坑,详见 HANDOFF 第 6 节)
- WSL2 走 Hyper-V 虚拟交换机,普通防火墙规则无效 → netsh portproxy 桥接
- SSH 不走 http_proxy → ~/.ssh/config 配 ProxyCommand
- 板端 dropbear 不收 ed25519 → 用 RSA 密钥 id_rsa_gw
